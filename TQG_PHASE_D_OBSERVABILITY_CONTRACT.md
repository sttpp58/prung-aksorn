# TQG Phase D — Observability Contract
**Contract:** D1
**Contract Version:** `TQG-OBS-01`
**Status:** LOCKED — Pre-Implementation
**Repository:** `sttpp58/prung-aksorn`
**Phase:** D — Observability & Operational Telemetry
**Baseline:** `main` at Phase C final engineering gate

---

## 1. Purpose

This document freezes the observability contract for TQG V1 before runtime instrumentation is implemented.

The contract defines:

- what TQG may report
- the stable event vocabulary
- required event fields
- derived metrics
- privacy constraints
- AI/cost accounting
- failure-isolation requirements
- compatibility and change rules

This contract is an observation boundary around the existing TQG workflow.

It does **not** authorize changes to TQG detection, classification, Inspector, Repair, re-validation, translation, storage, or Translation Job semantics.

---

## 2. Phase D Boundary

The locked runtime flow remains:

```
Completed Translation Output
        |
        v
Deterministic TQG Analysis
        |
        +--> PASS
        |
        +--> REVIEW / HIGH_SUSPICION
                    |
                    v
              Optional Inspector
                    |
                    v
            Confirmed Targeted Repair
                    |
                    v
             Mandatory Revalidation
```

Observability observes this flow:

```
TQG workflow
      |
      v
Observation Contract
      |
      v
Injected Observer / Sink
```

The observation layer is a passive consumer of TQG results.

## 3. Contract Principles

### 3.1 Passive observation

Telemetry must observe an existing decision rather than create or modify a decision.

```
TQG result -> telemetry
```

not:

```
telemetry -> TQG result
```

### 3.2 No behavior dependency

A TQG operation must succeed or fail according to its existing logic even when:

- no observer is configured
- the observer is disabled
- the observer throws
- the sink is unavailable
- an emitted event is rejected

### 3.3 No extra AI work

Instrumentation must not create additional:

- Inspector calls
- Repair calls
- translation calls
- transport calls

For an equivalent execution path, AI and transport counts must remain unchanged.

### 3.4 No content telemetry

The contract records operational metadata only.

Translation content is never a telemetry payload.

### 3.5 Deterministic schema

Field names, event names, enums, and privacy rules are versioned contract items.

An implementation must not silently add arbitrary payload fields.

---

## 4. Non-Goals

D1 does not implement:

- analytics dashboards
- persistent telemetry storage
- remote telemetry delivery
- user profiling
- content logging
- prompt/response archiving
- detector tuning
- threshold tuning
- new finding codes
- model/provider changes
- repair algorithm changes
- semantic quality scoring
- automatic remediation

A production telemetry backend, if desired later, requires a separate scope decision.

## 5. Event Vocabulary

The minimum locked event set is:

| Event | Meaning |
|---|---|
| `tqg.output.completed` | A completed translation output reached the TQG integration boundary. |
| `tqg.detection.completed` | Deterministic TQG analysis completed. |
| `tqg.inspector.completed` | An Inspector invocation completed, including an uncertainty/error outcome represented by status. |
| `tqg.repair.completed` | A Repair attempt reached a terminal outcome. |
| `tqg.revalidation.completed` | Mandatory repair re-validation reached a terminal outcome. |
| `tqg.error` | A TQG operational failure was classified for measurement. |

The contract intentionally uses terminal events for the minimum stable schema.

A future start-event model is not part of D1.

---

## 6. Common Event Fields

Every event must contain the following fields unless explicitly marked optional:

| Field | Type | Rule |
|---|---|---|
| `schemaVersion` | string | Must equal `TQG-OBS-01`. |
| `event` | string | Must be one of the locked event names. |
| `timestamp` | string | ISO-8601 timestamp generated by the observer boundary. |
| `phase` | string | Must be `D`. |
| `status` | string | Stable terminal status for the event. |
| `context` | string | `single`, `batch`, `recovery`, `manual`, or `unknown`. |

The timestamp is operational metadata only.

No user, book, chapter, paragraph, job, or device identifier is required by D1.

## 7. Controlled Enumerations

### 7.1 Status

The baseline event statuses are:

```
COMPLETED
PASS
REVIEW
HIGH_SUSPICION
ACCEPTED
REJECTED
ERROR
NOT_RUN
```

Only statuses semantically valid for an event may be emitted.

### 7.2 Verdict

When a verdict is applicable:

```
PASS
REVIEW
HIGH_SUSPICION
TRUE_ANOMALY
FALSE_POSITIVE
UNCERTAIN
```

### 7.3 Error class

Operational failures must use a stable category:

```
NONE
CONFIGURATION
TRANSPORT
TIMEOUT
VALIDATION
BOUNDARY
RUNTIME
OBSERVER
```

Implementation-specific exception names may be retained in local debugging but are not part of the public D1 telemetry contract.

### 7.4 Context

```
single
batch
recovery
manual
unknown
```

If the integration cannot establish the execution context without accessing protected application data, it must emit `unknown`.

## 8. Event-Specific Contract

### 8.1 `tqg.output.completed`

Required:

```
schemaVersion
event
timestamp
phase
status
context
```

Status must be:

```
COMPLETED
```

This event does not contain translation text or identifiers.

### 8.2 `tqg.detection.completed`

Required:

```
schemaVersion
event
timestamp
phase
status
context
verdict
findingCodes
findingCount
durationMs
```

Rules:

- `verdict` is PASS, REVIEW, or HIGH_SUSPICION.
- `findingCodes` contains only locked TQG finding codes.
- Each element of `findingCodes` represents one finding occurrence; the same code may appear more than once.
- `findingCount` equals `findingCodes.length` after TQG exception handling.
- `durationMs` is a non-negative numeric duration.
- `aiCalls` must be 0 for deterministic detection.

Optional:

```
aiCalls
transportCalls
```

Both must remain 0 for this event.

### 8.3 `tqg.inspector.completed`

Required:

```
schemaVersion
event
timestamp
phase
status
context
verdict
durationMs
aiCalls
transportCalls
```

Rules:

- When `status=COMPLETED`, `verdict` is TRUE_ANOMALY, FALSE_POSITIVE, or UNCERTAIN.
- When `status=ERROR`, `verdict` must be UNCERTAIN and `errorClass` is required.
- A transport/runtime failure uses `status=ERROR` and the appropriate `errorClass`.
- `aiCalls` counts actual Inspector AI invocations.
- `transportCalls` counts actual transport invocations.
- No content payload is permitted.

Optional:

```
findingCodes
findingCount
errorClass
```

### 8.4 `tqg.repair.completed`

Required:

```
schemaVersion
event
timestamp
phase
status
context
durationMs
aiCalls
transportCalls
accepted
```

Rules:

- `status` is ACCEPTED, REJECTED, or ERROR.
- `accepted=true` is permitted only when the existing Repair pipeline reports an accepted result after its mandatory re-validation.
- `accepted=false` is required for REJECTED and ERROR outcomes.
- Boundary rejection must remain a REJECTED or ERROR operational outcome according to existing Repair semantics.
- No replacement text is emitted.

Optional:

```
findingCodes
findingCount
errorClass
revalidated
```

### 8.5 `tqg.revalidation.completed`

Required:

```
schemaVersion
event
timestamp
phase
status
context
durationMs
revalidated
```

Rules:

- `status=COMPLETED` means the re-validation operation reached its terminal result.
- `status=ERROR` is used when re-validation itself fails operationally.
- `revalidated=true` means the existing re-validation result passed.
- `revalidated=false` means the existing re-validation result failed, rejected the repair, or could not complete successfully.
- This event does not authorize bypassing re-validation.

Optional:

```
findingCodes
findingCount
errorClass
```

### 8.6 `tqg.error`

Required:

```
schemaVersion
event
timestamp
phase
status
context
errorClass
```

Rules:

- `event` is tqg.error.
- `status=ERROR`.
- `errorClass` is one of the locked categories.
- Error messages must not include raw prompts, responses, source text, target text, secrets, or credentials.

Optional:

```
durationMs
aiCalls
transportCalls
```

## 9. Finding Code Contract

D1 does not create or alter finding semantics.

The only valid `findingCodes` are the existing V1 codes:

```
FOREIGN_SCRIPT_SPAN
SOURCE_LANGUAGE_RESIDUE
SOURCE_TEXT_OVERLAP
MIXED_LANGUAGE_SPAN
PROMPT_LEAKAGE
REPEATED_TEXT
STRUCTURAL_TRUNCATION
PARAGRAPH_LOSS
QUOTE_ANOMALY
PUA_OR_REPLACEMENT_CHAR
```

Telemetry may count these codes.

Telemetry must not introduce:

```
new detector code
replacement detector code
renamed detector code
free-form content label
```

A missing finding-code mapping must not be invented by the observer.

## 10. AI and Transport Accounting

D1 requires measurable counts where the existing TQG operation can expose them reliably.

### Required counters

```
aiCalls
transportCalls
```

Interpretation:

- deterministic TQG detection: `aiCalls=0`, `transportCalls=0`
- Inspector: actual Inspector call count
- Repair: actual Repair call count
- re-validation: no AI call is implied by this contract

The observer must report observed counts, not estimated counts.

Token or monetary cost is not required at D1 when reliable provider metadata is unavailable.

If provider metadata becomes available later, cost instrumentation must be added without logging prompt or response content.

## 11. Performance Measurement Contract

Every operation for which latency is measured uses:

```
durationMs
```

Requirements:

- numeric
- finite
- non-negative
- measured around the existing operation
- instrumentation time must not be included as application work unless explicitly identified by the benchmark

D1 defines event-level measurement only.

Derived statistics are calculated outside the TQG decision path.

Required derived metrics for Phase D are:

```
count
average
p50
p95
p99
max
```

for applicable operation durations.

D1 does not define an acceptance threshold for production latency.

Acceptance thresholds are a later Phase D performance/gate decision based on observed baseline evidence.

## 12. Privacy Contract

The following fields are permanently prohibited from D1 event payloads:

```
sourceText
targetText
translationText
suspiciousText
fullFindingText
fullPrompt
systemPrompt
userPrompt
rawAIResponse
replacementText
glossaryText
glossaryContents
bookTitle
chapterTitle
chapterText
sourceChapter
userId
email
credentials
API keys
authorization headers
cookies
session tokens
backup payloads
recovery payloads
```

A telemetry implementation must also reject dynamically supplied payload keys that are clearly content-bearing or secret-bearing.

The absence of a forbidden field must be tested, not assumed.

---

## 13. Privacy-by-Design Rules

1. Telemetry records metadata, not translation content.
2. Raw error objects must not be serialized wholesale.
3. Raw provider responses must never be forwarded to the observer.
4. Secret-bearing headers must never be forwarded.
5. Glossary text is content and is therefore excluded.
6. No identifier is required merely for correlation.
7. Any future correlation identifier requires a separate privacy review.
8. Public repository fixtures must not contain private real-world translation content.

D1 makes no claim that the application as a whole is privacy-perfect; it defines the TQG observability boundary only.

## 14. Observer / Sink Contract

The runtime implementation should expose an injected observer abstraction conceptually equivalent to:

```js
observer.emit(event)
```

Required behavior:

- `emit` accepts a D1-compliant event.
- The observer may be disabled.
- A missing observer behaves as a no-op.
- Observer failure must be isolated from TQG.
- The TQG result must not depend on sink acknowledgement.
- The observer must not initiate translation, Inspector, Repair, storage, or checkpoint work.

The sink implementation is not fixed by D1.

Permitted implementations include:

```
no-op
in-memory test sink
local diagnostic sink
future production sink
```

D1 does not authorize a persistent database or remote analytics service.

---

## 15. Required Invariants

The following invariants are mandatory:

### I1 — Decision preservation

For identical inputs and the same decision path:

```
TQG result before observability
==
TQG result after observability
```

### I2 — AI-call preservation

```
aiCalls(after instrumentation)
==
aiCalls(before instrumentation)
```

unless an explicit pre-existing application path changed outside Phase D.

### I3 — Transport-call preservation

Instrumentation must not add network/transport work.

### I4 — Fail-open observer boundary

```
observer failure
        ↓
TQG continues with existing result
```

### I5 — Re-validation preservation

Telemetry cannot mark a repair as valid.

Only existing re-validation logic may determine re-validation status.

### I6 — Repair preservation

Telemetry cannot approve, reject, expand, or shrink a repair span.

### I7 — Storage isolation

Telemetry does not alter application storage schema or Translation Job state.

## 16. Derived Metrics

Phase D may derive metrics from compliant event streams.

Minimum required metrics:

| Metric family | Required measurements |
|---|---|
| Volume | completed outputs |
| Verdict | PASS / REVIEW / HIGH_SUSPICION |
| Findings | count by finding code |
| Inspector | invoked / completed / error |
| Inspector usage | AI calls / transport calls |
| Repair | accepted / rejected / error |
| Repair usage | AI calls / transport calls |
| Revalidation | pass / fail |
| Errors | count by error class |
| Performance | average / p50 / p95 / p99 / max |
| Context | single / batch / recovery / manual / unknown |

Derived metrics must retain their denominator and event population so that Phase E does not confuse sample-stratified observations with production prevalence.

D1 does not define production-prevalence estimates.

## 17. Event Validation Rules

Before an event reaches a sink, the observer layer must validate at least:

```
schemaVersion is exact
event is recognized
phase is D
status is valid for the event
context is valid
numeric fields are finite and non-negative
findingCodes contain only locked codes
forbidden content keys are absent
```

Invalid telemetry must be rejected or sanitized without affecting TQG execution.

A telemetry validation failure is an observer-layer failure, not a TQG quality failure.

## 18. Versioning and Change Control

### Locked items

The following are D1 contract items:

- schema version
- event names
- common field names
- controlled enums
- finding-code vocabulary
- privacy deny-list
- AI/transport counter meaning
- observer isolation rules
- invariant definitions

Changing one of these requires a new explicit contract revision.

### Additive change

A future contract revision may add an optional field only when:

- it is non-content metadata
- it has a defined type and privacy rule
- old consumers can safely ignore it
- it does not alter TQG behavior

### Breaking change

Changing any required field meaning, event meaning, enum semantics, or privacy boundary is a breaking contract change.

Breaking changes require:

```
new contract version
scope review
Deep Review 3/3
regression
explicit commit
```

D1 must not be silently modified during D2 implementation.

## 19. Implementation Prohibitions

D2 implementation must not use the D1 contract as justification to:

- add raw translation logging
- add prompt logging
- add AI response logging
- add a telemetry database
- modify IndexedDB for telemetry
- add tracking identifiers
- change TQG thresholds
- add finding codes
- modify classifier rules
- change Inspector prompts
- change Repair prompts
- change repair boundaries
- bypass re-validation
- introduce an AI call for telemetry
- introduce a remote analytics dependency into TQG core

These are scope changes.
