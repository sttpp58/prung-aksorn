# รีวิว "ปรุงอักษร" — ห้องทำงานนักแปล/บรรณาธิการนิยาย

แอปเว็บส่วนตัวสำหรับแปลนิยาย/ขัดสำนวนภาษาไทย เชื่อมต่อ AI ของผู้ใช้เอง (OpenAI/Gemini) พัฒนาเป็นไฟล์ HTML เดียว (~4,000 บรรทัด) hosting ผ่าน GitHub Pages เป็น PWA ติดตั้งใช้งานได้จริง

---

## 1. ฟีเจอร์หลัก: แปล/ขัดสำนวน

- สลับโหมด "ต้นฉบับภาษาอื่น (แปล)" กับ "ไทยอยู่แล้ว (ขัดสำนวน)"
- ปรับได้ 3 มิติ: ระดับการปรับ (พิสูจน์อักษร/เรียบเรียง/ขัดเกลาใหม่), แนวเรื่อง (ทั่วไป/แฟนตาซี/โรแมนซ์/สืบสวน/ไซไฟ/กำลังภายใน), สำนวนภาษา (ปัจจุบัน/ย้อนยุค/ร่วมสมัย/ทางการ)
- **แบ่งข้อความยาวเป็น chunk อัตโนมัติ** ตัดตามย่อหน้าก่อน ถ้าย่อหน้าเดียวยาวเกินตัดตามประโยค (รองรับเครื่องหมายจีน 。！？ ด้วย) ถ้ายังยาวเกินตัดดิบตามความยาว — การันตีไม่มี chunk ไหนเกินขนาดที่ตั้งไว้
- **ต่อเนื่องข้าม chunk**: ส่งท้ายข้อความ (300 ตัวอักษรสุดท้าย) ของ chunk ก่อนหน้าไปเป็นบริบทให้ AI ทุกครั้ง กันรอยต่อสะดุด
- **Retry อัตโนมัติ** เมื่อเจอ error ชั่วคราว (429/5xx/เน็ตหลุด) สูงสุด 2 ครั้งแบบ exponential backoff, แยกจาก error ถาวร (key ผิด/โมเดลไม่มีจริง) ที่ error ทันทีไม่ retry
- **แปลต่อจากที่ค้าง**: ถ้า retry ครบแล้วยัง fail จำ chunk ที่เสร็จแล้วไว้ ให้กดทำต่อจากจุดที่พังได้โดยไม่ต้องเริ่มใหม่ทั้งเรื่อง
- **ยกเลิกกลางทางได้** ผ่าน `AbortController`
- แก้ไขผลลัพธ์ตรงๆ ได้ (`contenteditable`) แล้ว "บันทึกฉบับแก้ไข" เป็นประวัติใหม่ พร้อมผูก `parentId` ไว้เทียบเวอร์ชันย้อนหลังได้

## 2. ซ่อม OCR / Smart Paste (วางปุ๊บ ซ่อมปั๊บ)

- **Smart Paste (วางปุ๊บ รู้ใจปั๊บ):** เมื่อคัดลอกต้นฉบับมาวาง (Paste) ระบบจะแอบทำงานเบื้องหลัง 2 อย่างทันที:
  1. คลีนอักขระ PUA (ปัญหาพยัญชนะ ก ง จ ด ค น ม ร หาย) และสัญลักษณ์ขยะ (□■◆◇) ออกให้แบบเรียลไทม์ 
  2. ใช้ Regex สแกนบรรทัดแรก หากเจอคำแนวหัวข้อ (เช่น ตอนที่, Chapter, 第...章, บทนำ) จะ **"ดูด"** ไปใส่ช่องชื่อตอนให้อัตโนมัติ และตัดออกจากเนื้อหาหลักเพื่อไม่ให้ AI แปลซ้ำซ้อน
- `normalizeOCR()` ฟังก์ชันหลักสำหรับแก้ปัญหาฟอนต์เก่าถอดรหัสเพี้ยน ยืนยันความถูกต้องแล้วจริงด้วยการวิเคราะห์ไฟล์ตัวอย่าง OCR 
- มีปุ่ม "ซ่อม OCR ด้วย AI" สำหรับให้โมเดลภาษาช่วยเกลาคำผิดจากการสแกน พร้อม `highlightSuspicious()` ไฮไลต์บรรทัดที่มีสัญลักษณ์แปลกๆ

## 3. จัดการเรื่อง → เล่ม → ตอน

- โครงสร้างสามชั้น: เรื่องนิยาย (`project`) → เล่ม (`book`) → ประวัติการแปลแต่ละตอน (`history`)
- คลังคำเฉพาะเรื่อง + บริบทเรื่อง อยู่ระดับ "เรื่อง" ใช้ร่วมกันทุกเล่ม/ตอน ส่งแนบไปกับทุกคำขอแปลเพื่อความสม่ำเสมอของชื่อตัวละคร/สถานที่
- **AI ช่วยดึงคลังคำ**: สแกนทั้งข้อความ (ไม่ใช่แค่ท่อนแรก) แบ่ง chunk เหมือนตอนแปล พร้อม `dedupeGlossary()` ตัดคำซ้ำแบบไม่สนตัวพิมพ์เล็ก-ใหญ่
- **ตัดแบ่งตอนอัตโนมัติ**: `detectChapterSplits()` จับรูปแบบหัวข้อตอน ตอนนำเข้าไฟล์เดียวยาวๆ ถามยืนยันก่อนแบ่งเสมอ ไม่บังคับ
- **นำเข้าหลายไฟล์**: เลือกได้หลาย .txt พร้อมกัน แปลทีละไฟล์อัตโนมัติ บันทึกแยกประวัติตามชื่อไฟล์
- ค้นหาในประวัติแบบ real-time ตามชื่อตอน
- **เทียบเวอร์ชัน (diff)**: ปุ่ม Δ เทียบฉบับแก้ไขกับต้นทางที่แก้มา ไฮไลต์คำที่เพิ่ม/ลบด้วย LCS diff ระดับคำ
- **ตัวตรวจสอบความสม่ำเสมอ**: ให้ AI สแกนทุกตอนในเล่มเทียบกับคลังคำ รายงานจุดที่ชื่อตัวละคร/สถานที่สะกดไม่ตรงกัน

## 4. ประเมินค่าใช้จ่ายและคิวการทำงาน (Token / Cost Tracker)

- **Chunk Predictor (ประเมินคิวส่ง AI):** ใต้กล่องข้อความจะคำนวณแบบเรียลไทม์ว่าความยาวอักขระปัจจุบันจะต้องถูกซอยเป็น "คิวส่ง AI กี่ส่วน" ช่วยให้ผู้ใช้วางแผนเวลารอได้
- **Live API Cost Tracker:** แถบป้ายราคามุมขวาบน (`$0.0000`) คอยนับยอดค่าใช้จ่ายสะสมจากการใช้ Token จริง (ดึงยอด Usage จาก API โดยตรง คำนวณตามเรต GPT-5o-mini, Gemini 3.6 flash  ล่าสุด)
- **Session Report:** สรุปยอด Token และค่าใช้จ่ายรายครั้งเมื่อกดแปล, ซ่อมข้อความ, หรือดึงคลังคำเสร็จสิ้น

## 5. โหมดนักอ่าน + อ่านออกเสียง

- รวมทุกตอนในเล่มเป็นหน้าอ่านเดียวต่อเนื่อง พร้อมสารบัญ (TOC) แบบ drawer
- จำตำแหน่งอ่านค้างไว้ต่อเล่ม (debounce 500ms ระหว่างเลื่อน + force-save ทันทีตอนปิดหน้าต่าง กันคลาดเคลื่อน)
- ปรับขนาดฟอนต์ได้ (14-32px), sync dark mode กับหน้าหลัก
- **Text-to-Speech** ผ่าน Web Speech API (ไม่มีค่าใช้จ่ายเพิ่ม): เล่น/หยุดชั่วคราว/หยุด/ย่อหน้าก่อน-ถัดไป, ปรับความเร็ว 0.6-2x, เลือกเสียง (แยกกลุ่มเสียงไทยขึ้นก่อน), ไฮไลต์ + เลื่อนจอตามย่อหน้าที่กำลังอ่าน, อ่านต่อเนื่องข้ามตอนอัตโนมัติ

## 6. Export & สำรองข้อมูล

- Export .DOCX / .EPUB ต่อเล่ม (ประกอบ XML/manifest/spine ของ epub ถูกสเปกจริง)
- โหลดไลบรารี docx/jszip/file-saver จาก CDN แบบ **SRI-pinned** (ตรวจสอบ hash แล้วว่าตรงกับไฟล์จริงจาก npm 100%) พร้อม fallback ข้าม CDN (jsDelivr → unpkg) และข้ามไฟล์ (umd → iife)
- Export/Import ข้อมูลทั้งหมดเป็นไฟล์ JSON backup แยกจาก localStorage ของเบราว์เซอร์

## 7. ความทนทานของระบบ

- **PWA ใช้งานออฟไลน์ได้บางส่วน**: Service Worker cache เฉพาะไฟล์ app shell เอง ไม่แตะการเรียก AI API/Google Fonts (กันแคชคำแปลผิดๆ ค้าง)
- **เตือนพื้นที่ localStorage**: ประเมินขนาดข้อมูลก่อนเต็ม (>4MB เตือนล่วงหน้า) และดักจับตอน `setItem` fail จริง (>เต็มจริง) แสดง dialog แนะนำให้ backup ทันที
- **`saveData()` debounce 400ms** ลดภาระ `JSON.stringify` ก้อนข้อมูลใหญ่ซ้ำๆ ตอนมีการแก้ข้อมูลถี่ๆ พร้อมระบบ `saveDataImmediate()` ที่บังคับบันทึกข้อมูลสำคัญทันที (เช่น ตอน Import ข้อมูลกู้คืน) เพื่อป้องกันปัญหาข้อมูลเก่าทับข้อมูลใหม่เนื่องจากจังหวะหน่วงเวลา

## 8. คุณภาพโค้ด / สถาปัตยกรรม

- **`commitChange()`**: รวม save+render สองจุด (sidebar + แผงล่าง) ที่เคยพิมพ์ซ้ำมือ 15 จุดทั่วไฟล์ ให้เหลือจุดเดียว ลดความเสี่ยงลืม render หลังแก้ข้อมูล
- **ห่อทั้งแอปด้วย IIFE** กัน global scope ชนกันในอนาคต 
- **Unit test 24 เคส** ครอบคลุมฟังก์ชัน pure logic ทั้งหมด 10 ตัว ดึงซอร์สจาก `index.html` จริงมาทดสอบโดยตรง รันด้วย `node test/run-tests.js` 
- **Custom dialog system**: แทนที่ `alert`/`prompt`/`confirm` มาตรฐานเบราว์เซอร์ทั้งหมด (0 จุดเหลือ) ด้วย dialog ธีมเดียวกับแอป (Promise-based, รองรับ Enter/Escape)
- **ไอคอนทั้งแอปเป็น SVG เส้นสีเดียว** ไม่มีอิโมจิสีปนแล้ว บุคลิกภาพนิ่งเป็นชิ้นเดียวกัน

## ข้อจำกัด

| จุด | รายละเอียด |
|---|---|
| Consistency checker ข้าม batch | เล่มยาวมากจนต้องแบ่งส่งหลายรอบ จะตรวจความสม่ำเสมอข้าม batch ไม่ได้ |
| ตัดแบ่งตอนอัตโนมัติ | จับได้เฉพาะรูปแบบหัวข้อที่รู้จัก (Regex ดักคำฮิตไว้แล้ว) ถ้าไฟล์ใช้รูปแบบแปลกกว่านี้จะไม่แบ่งให้ |

## สรุป

แอปนี้ครบทุกด้านของงานแปลนิยายจริงจังแล้ว: **แปล/ขัดสำนวนที่ปรับละเอียดได้**, **จัดการหลายเล่มหลายตอนเป็นระบบ**, **อ่านทวนสบายตาพร้อมฟังได้**, **ส่งออกเป็นไฟล์ใช้งานจริง**, **คำนวณต้นทุน API ได้เอง**, และ **มีเครื่องมือ QA ของตัวเอง** (diff, consistency checker, smart paste) ที่หลายเครื่องมือแปลเชิงพาณิชย์ยังไม่มีให้ด้วยซ้ำ 

ด้านความทนทานของระบบก็อยู่ในระดับที่เกินความคาดหวังของ "เครื่องมือส่วนตัว" ไปมาก (retry, resume, SRI-pinned CDN, quota warning, unit test, runtime smoke test) จุดที่ยังไม่สมบูรณ์ล้วนเป็น nice-to-have ที่รู้ตัวและมีแผนอยู่แล้ว ไม่มีจุดไหนที่เป็น "ความเสี่ยงซ่อนอยู่" ที่ยังไม่ถูกพูดถึง
